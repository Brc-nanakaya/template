# To-Do タスク管理アプリ 構築ガイド

> このプロジェクトの目的は **フロントエンド / バックエンド / API といったクラウドの仕組みを学ぶ** ことです。
> 本ドキュメントは次の 2 軸で構成しています。
>
> 1. **どのファイルがどこに配置されているのか**（テンプレートの地図）
> 2. **どのような指示を出せば To-Do 管理システムが構築できるのか**（AI への指示のレシピ）

---

## 0. まず全体像を 3 つの言葉で

Web アプリは大きく 3 つの層でできています。To-Do アプリで例えると次の通りです。

| 層 | 役割 | To-Do アプリでの例 | このテンプレートでの置き場所 |
| --- | --- | --- | --- |
| **フロントエンド** | 画面・見た目・操作 | 「タスク一覧」「追加ボタン」「チェックボックス」 | `app/`・`components/` |
| **バックエンド / API** | データの保存・取得・加工 | 「タスクを保存する」「一覧を返す」 | `app/api/.../route.ts` |
| **ロジック（共通部品）** | 計算・変換・ルール | 「未完了だけ絞り込む」「日付を整形する」 | `lib/` |

このテンプレートでは **Next.js** という枠組みを使い、フロントエンドとバックエンドを **1 つのプロジェクトの中** に同居させています。これがいわゆる「フルスタック」構成で、クラウド上では 1 つのアプリとしてデプロイ（公開）されます。

## 1. どのファイルがどこに配置されているのか

### 1-1. ディレクトリの地図

```
template/
├── app/                      ★ 画面とAPIの本体（Next.js App Router）
│   ├── layout.tsx            全ページ共通の枠（フォント・通知トースト設定）
│   ├── page.tsx              トップページ ＝ いま最初に編集する画面
│   ├── globals.css           全体のスタイル（Tailwind + テーマ色）
│   ├── ai-samples/           AIサンプル画面（今回のTo-Doでは未使用でOK）

│   └── api/                  ★ バックエンドAPIの置き場所
│       └── ai/
│           ├── workflow/route.ts   APIの「お手本」（POSTで受けてJSONを返す）

├── components/               ★ 画面の部品（再利用するUIパーツ）
│   └── ui/

│

│   ├── unit/                 ロジック単体テスト（Vitest）
│   │   └── utils.test.ts     lib/utils.ts のテスト例
│   └── e2e/                  画面操作テスト（Playwright）
│       └── home.spec.ts      トップページの表示テスト例
│
├── public/                   画像など静的ファイル
├── process.md                ★ 開発の進め方を記録するテンプレ（要件・タスク表）
```

★ 印が、To-Do アプリを作るときに **実際に触るフォルダ** です。

### 1-2. 「どこに何を書くか」の判断ルール

迷ったら次の表で判断します。これが本テンプレートの設計思想そのものです。

| やりたいこと | 置く場所 | ファイル例 |
| --- | --- | --- |
| 画面（ページ）を増やす | `app/<名前>/page.tsx` | `app/todos/page.tsx` |
| 画面の部品を切り出す | `components/` | `components/TodoItem.tsx` |
| 計算・絞り込み・変換ルール | `lib/` | `lib/todo.ts` |
| データを保存/取得するAPI | `app/api/<名前>/route.ts` | `app/api/todos/route.ts` |
| ロジックのテスト | `tests/unit/` | `tests/unit/todo.test.ts` |
| 画面操作のテスト | `tests/e2e/` | `tests/e2e/todo.spec.ts` |

**学びのポイント**: 「画面 (`app`)」「頭脳 (`lib`)」「API (`app/api`)」を分けるのは、
**役割ごとに分離しておくと、テストしやすく・直しやすくなる** からです。
たとえば「未完了タスクだけ数える」処理を `lib/todo.ts` に置けば、画面を立ち上げずに `tests/unit/` で正しさを検証できます。

### 1-3. 既存ファイルから学ぶ「お手本」

新しく書く前に、テンプレートに入っている実物を読むと早いです。

- **画面の書き方** → [app/page.tsx](../app/page.tsx)
  （`data-testid` 属性が付いている点に注目。これは E2E テストから要素を見つける目印）
- **API の書き方** → [app/api/ai/workflow/route.ts](../app/api/ai/workflow/route.ts)
  （`POST` 関数で受け取り → 入力チェック → `NextResponse.json(...)` で返す、という型がそのまま To-Do API に流用できる）
- **共通部品の書き方** → [components/ui/tabs.tsx](../components/ui/tabs.tsx)
- **ロジックとテストの対応** → [lib/utils.ts](../lib/utils.ts) と [tests/unit/utils.test.ts](../tests/unit/utils.test.ts)

## 2. どのような指示を出せば To-Do 管理システムが構築できるのか

ここでは **AI（Claude Code）への指示の出し方** をレシピ化します。
ポイントは **「一気に全部」ではなく「層ごとに小さく」頼む** ことです。そうすると、各ステップで何が起きたのかを学べます。

### 2-0. 最初の 1 行（オリエンテーション）

> **指示例**
> 「`process.md` に、To-Do タスク管理アプリの要件・画面構成・タスク分解を埋めてください。
> 機能は『タスクの追加・一覧表示・完了チェック・削除』の 4 つにしてください。」

→ いきなりコードを書かせず、まず **設計を言語化** させます。[process.md](../process.md) がその受け皿です。

### 2-1. ステップ① フロントエンド（画面を作る）

> **指示例**
> 「`app/page.tsx` を書き換えて To-Do の画面を作ってください。
> ・テキスト入力＋『追加』ボタンでタスクを増やせる
> ・一覧をチェックボックス付きで表示し、完了は打ち消し線にする
> ・各タスクに削除ボタンを付ける
> ・まずはブラウザ内（React の state）だけでデータを保持する
> ・各要素に `data-testid` を付けてください」

**学べること**: React の state（画面が持つ一時的なデータ）、コンポーネント、イベント（クリック・入力）。
この段階では **まだサーバーは登場しません**。「画面だけで動くアプリ」を体感するのが狙いです。

### 2-2. ステップ② ロジックを切り出す（頭脳を分離する）

> **指示例**
> 「タスクの絞り込み（全件 / 未完了 / 完了）と件数集計のロジックを `lib/todo.ts` に切り出し、
> `app/page.tsx` からはそれを呼ぶだけにしてください。
> 併せて `tests/unit/todo.test.ts` にユニットテストを書いてください。」

**学べること**: 関心の分離、純粋関数、テスト駆動の感覚。
`npm test` を実行すると、画面を開かずにロジックの正しさを確認できます。

### 2-3. ステップ③ バックエンド / API（データをサーバーに置く）

> **指示例**
> 「タスクを保存・取得する API を `app/api/todos/route.ts` に作ってください。
> ・`GET` で全タスクを JSON で返す
> ・`POST { title }` で新規タスクを追加する
> ・`DELETE`・`PATCH` で削除・完了切り替えに対応する
> ・保存先はまずサーバーのメモリ（配列）で構いません
> [app/api/ai/workflow/route.ts](../app/api/ai/workflow/route.ts) の書き方に合わせてください。」

→ その後、画面側を「state 直書き」から「API を呼んでデータをやり取りする」形に変更してもらいます。

> **指示例（続き）**
> 「`app/page.tsx` を、上で作った `/api/todos` を `fetch` で呼ぶ形に変更してください。」

**学べること（ここがクラウドの核心）**:
- **フロントエンドとバックエンドは別々**で、`fetch`（HTTP リクエスト）で会話する
- API は **GET/POST/PATCH/DELETE** という「動詞」でやることを表す（REST の考え方）
- ブラウザを閉じてもサーバー側にデータが残る（＝ サーバーがデータの持ち主）

### 2-4. ステップ④ データを永続化する（任意・発展）

> **指示例**
> 「いまサーバーのメモリに置いているタスクを、再起動しても消えないようにしたいです。
> まずは JSON ファイル保存で実装し、将来データベースに差し替えられる形にしてください。」

**学べること**: 「メモリ＝消える / ファイル・DB＝残る」の違い。クラウドで本番運用するときにDBが要る理由。

### 2-5. ステップ⑤ テストで品質を守る

> **指示例**
> 「To-Do の主要操作（追加→完了→削除）を確認する E2E テストを `tests/e2e/todo.spec.ts` に書いてください。
> [tests/e2e/home.spec.ts](../tests/e2e/home.spec.ts) の書き方に合わせ、`data-testid` で要素を特定してください。」

**学べること**: 自動テストで「壊れていないこと」を毎回確認する習慣。

### 2-6. ステップ⑥ 動作確認・公開

> **指示例**
> 「`npm run dev` で開発サーバーを起動して、ブラウザで動作を確認させてください。」
> 「`npm run build` が通るか確認してください（＝ 本番公開できる状態か）。」

**学べること**: 開発サーバーと本番ビルドの違い。クラウドへデプロイする前段階。

## 3. 指示出しのコツ（学習効果を高めるために）

1. **層を 1 つずつ**: 画面 → ロジック → API → 永続化、の順で頼む。各段階で「何が変わったか」を確認する。
2. **置き場所を指定する**: 「`lib/` に切り出して」「`app/api/todos/route.ts` に」と **ファイルパスまで指示**すると、第 1 章の構成が身につく。
3. **お手本を参照させる**: 「`route.ts` の書き方に合わせて」と既存ファイルを指す。
4. **テストとセットで頼む**: ロジックを書いたら必ずユニットテストも依頼する。
5. **分からない用語は説明させる**: 「`fetch` とは何か、なぜ必要か説明して」と聞くと、コードと概念が結びつく。

## 4. 全体の流れ（早見表）

| # | ステップ | 主に触るファイル | 学べる概念 |
| --- | --- | --- | --- |
| 0 | 設計を言語化 | `process.md` | 要件定義・画面設計 |
| 1 | 画面を作る | `app/page.tsx`・`components/` | フロントエンド / React state |
| 2 | ロジック分離 | `lib/todo.ts`・`tests/unit/` | 関心の分離・ユニットテスト |
| 3 | API を作る | `app/api/todos/route.ts` | バックエンド / REST API / fetch |
| 4 | 永続化 | API + 保存先 | メモリ vs DB・クラウドのデータ |
| 5 | E2E テスト | `tests/e2e/` | 品質保証・自動テスト |
| 6 | 起動・ビルド | （コマンド） | 開発環境 vs 本番・デプロイ |
